# Language / i18n

**English and Turkish, chosen automatically by the browser.** Chrome's built-in
`chrome.i18n` is used; there is no separate language setting.

```bash
npm run check:i18n    # locale parity — missing, extra and dead keys
```

| File | Role |
|---|---|
| `_locales/en/messages.json` | **default_locale** — every language other than `tr` sees this |
| `_locales/tr/messages.json` | users whose Chrome UI language is Turkish |
| `src/shared/i18n.js` | `t(key)` and `localizeDom()` — fills the DOM from `data-i18n` attributes |

## Usage

- **HTML:** `data-i18n="key"` → `textContent` · `data-i18n-html="key"` → `innerHTML`
  (when the message contains `<code>` or `<strong>`) · `data-i18n-attr="title:key"` →
  an attribute · `<html data-i18n-title="key">` → the page title
- **JS:** `t('key')`, or `t('key', [value])` when there is a runtime value
- **`manifest.json`:** placeholders such as `__MSG_extName__`

## How the language is chosen

From Chrome's **UI language** (`chrome.i18n.getUILanguage()`) — not from the page's
language and not from the operating system's. Turkish if Chrome is Turkish, English for
everything else.

> **Decision (11 Aug 2026): there is no language picker.** The browser language was
> judged sufficient; the user is not asked to choose one by hand. That is the thing
> which makes `chrome.i18n` appropriate — it has no runtime override API anyway.
>
> If that decision reverses, the cost is: drop `chrome.i18n` and write a dictionary
> layer. The `data-i18n` attribute structure and `localizeDom()` stay exactly as they
> are; only the source behind `t()` changes from `chrome.i18n.getMessage` to our own
> JSON, plus the chosen language kept in `storage.local`. A cheap reversal — which is
> why nothing extra is being built for it today.

## A missing key produces silence, not an error

`chrome.i18n.getMessage()` does not throw for a key that does not exist; it returns an
empty string. `t()` shows the key itself in that case so the gap is visible during
development, and `npm run check:i18n` catches it as a step outside the build.

## The one that made the extension unloadable

`$NAME$` is **reserved** syntax in Chrome's i18n schema: if it appears in a message,
that message must also declare a `placeholders` block. Substitution was being done in
JS, so no placeholder was declared — and Chrome rejected the **entire extension** at
manifest validation with `Variable $N$ used but not defined. Could not load manifest.`

The fix was to leave `$…$` behind and use a neutral token such as `{n}` (a literal
dollar is written `$$`).

`check:i18n` now validates message syntax as well, and `npm run pack` will not produce a
zip without running all three checks — so a broken package cannot be built. Full write-up
in [field note 6](mv3-field-notes.md).
